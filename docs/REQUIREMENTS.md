记录日期：2026-09-06。本文承接本轮用户访谈及后续批准，供新对话直接继续。具体命令和数据结构以 [SPEC.md](SPEC.md) 为准，完成证据以 [DELIVERY.md](DELIVERY.md) 为准。

## 用户要达到的结果

| 已确认要求 | 当前落点 |
| --- | --- |
| 主要在 Mac、Windows、Linux 之间同步 | 首批 Mac、HomeServer、Shenzhen 已接入；Windows 设备暂不可连接，用户要求延后 |
| 每台设备都能维护全部设备的 Skills | 同一个 GitHub 私有数据仓，每台设备完整 checkout，均可修改共享内容及其他设备的配置 |

| 个人 Skills 连同所需资源完整同步 | 以目录包管理入口、参考资料、脚本、模板及必要共享 runtime；凭据与机器运行状态留在本地 |
| 修改都由联网 AI 完成 | 不建设离线编辑产品；维护前对账、修改后主动发布，冲突修复后才能完成 |
| 避免 AI 思考时发布半成品 | 持久编辑标记暂停后台；显式 finish 发布；任务外由 60 秒静默窗口补漏 |

| 先让自己的几台设备可用 | 当前验收以三台实际设备为准，不扩展公众服务和网页产品 |
| 已发布和已应用分别说明 | 发布核对 GitHub main；应用核对实际设备收据，没有设备证据时报告未知 |

Mac 仅作为首次整理与导入基准，接入后各端平等。设备离线不阻塞其他设备发布，重新上线后自行同步。
通用、操作系统、设备三级版本足够首期使用；项目级差异和多 AI 工具格式转换延后。

## 已批准的方案调整

1. 用户明确选择“以 SkillStow 为基线”。原 SkillRiver 早期方案的 Hub、签名、changeset、PR 强制审批与中心回执协议退出实现方案；保留的是上面的个人多设备需求。
2. 当前采用 Git main、CLI 校验、AI 维护 Skill 和本机钩子。私有内容发布不要求创建 PR；本代码仓的开发 PR 是另一件事。该流程不声称能拦截绕过 CLI 的直接 Git 操作。
3. 既有个人体系存在共享 runtime 依赖，首次按每设备一个完整体系包迁移，保留设备 manifest、overlay 与资源。以后只有确有独立生命周期的 Skill 才逐步拆包。
4. 用户授权大胆精简 Mac Skills：移除重复通用约束、情绪驱动和固定审核轮次等流程负担，保留必要经验、资源和工具能力。该轮已完成；后续根据实际使用结果定向调整，不因换模型自动重写全部 Skills。
5. 当前项目接续目录是 `SkillStow`。用户口述“SkillsStore”指此项目；旧项目目录由用户自行删除。

## 尚未完成与不再追求的事项

Windows 仍需在设备可连接后适配私人 runtime 的 Unix 依赖、安装后台任务并完成真实双向维护及客户端识别验收。已有 junction 代码和历史平台探针不能替代当前整条链路验收。

公众平台、Hub、签名治理和网页控制台不是剩余必做项。三设备已验收也不等于每个 Skill 的外部账号、服务和 AI 客户端都已逐项执行验证。
